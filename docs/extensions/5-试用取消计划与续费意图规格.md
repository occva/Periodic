# 试用、取消计划与续费意图规格

> 版本：1.0｜日期：2026-09-23｜状态：方案设计，尚未实现。
> 依赖：[需求文档](../requirement.md)、[架构说明](../architecture.md)、[扩展规格总则](README.md)。

## 1. 目标与核心边界

本功能补充订阅从试用、继续使用到计划取消的决策信息，但不改变现有管理状态、到期状态和付款事实的定义。

以下概念必须分开：

| 概念 | 回答的问题 | 是否自动改变其他事实 |
| --- | --- | --- |
| 管理状态 | 用户是否仍管理这条记录 | 否 |
| 到期状态 | 当前访问权是否已超过到期日 | 否 |
| 续费意图 | 用户目前准备继续、取消还是尚未决定 | 否 |
| 试用阶段 | 当前是否处于一段明确试用期 | 否 |
| 取消计划 | 何时前需要操作、是否已提交及何时结束访问 | 否 |
| 实际付款 | 用户是否确认发生付款 | 只能由付款操作写入 |

因此：

- “到期取消”期间订阅仍可处于 active，继续参与到期前的有效数量和费用口径；
- 试用结束不会自动生成付款、周期、续费或价格变化；
- 取消截止日到达不会自动停用或删除订阅；
- Provider、通知或日期任务不能替用户确认已取消或已付款。

## 2. 续费意图

### 2.1 类型

```swift
enum RenewalIntent: String, Codable, Sendable, CaseIterable {
    case undecided
    case continueUsing
    case cancelAtPeriodEnd
}
```

- `undecided`：尚未记录决定，也是旧数据迁移后的默认值。
- `continueUsing`：用户计划继续使用；不代表已经付款或服务一定会自动扣款。
- `cancelAtPeriodEnd`：用户计划在当前周期结束时停止；不代表已向服务商提交取消。

续费意图只适用于 recurring。lifetime 固定为“不适用”，不得用 `continueUsing` 表示永久有效。

### 2.2 行为规则

- 修改意图是普通订阅字段更新，必须携带 expected revision。
- 设为 `cancelAtPeriodEnd` 时建议创建取消计划，但允许仅记录意图；界面明确提示“尚未确认已取消”。
- 完成续费时，如原意图为 `cancelAtPeriodEnd` 或存在未结束取消计划，必须先在同一确认流程中选择撤回计划或返回，不得静默清除。
- 完成续费后默认保留 `continueUsing`；用户也可在确认页改为 `undecided`。
- 停用不删除续费意图和历史计划；恢复 active 后继续展示，但重新调度前必须核对日期是否仍有效。
- 切换为 lifetime 时，保存前展示将结束试用和未完成取消计划的影响；确认后把计划标记为 `closedByBillingKindChange`，不直接删除历史。

## 3. 试用计划

### 3.1 数据

`TrialPlanRecord`：

| 字段 | 约束 |
| --- | --- |
| id / subscriptionID | 稳定 UUID 和父订阅 UUID |
| startDay / endDay | 本地 Gregorian 日期，必填，首尾包含且 start ≤ end |
| cancellationDeadlineDay | 可空；存在时不得晚于 endDay |
| postTrialBehavior | autoRenews / manualDecision / unknown |
| state | active / converted / cancelled / expiredUnresolved |
| note | 可选；不进入通知正文和普通日志 |
| revision / createdAt / updatedAt | 并发与审计字段 |

同一订阅最多有一个 active 试用计划，但历史试用记录可以保留。试用是生命周期事实，不新增第三种 `billingKind`；试用中的项目仍是 recurring。

### 3.2 状态变化

- 创建时必须明确结束日，不根据“首月免费”等自然语言猜日期。
- 今天处于 `startDay...endDay` 且 state=active 时显示“试用中”。
- 到达 endDay 次日仍未确认结果时，派生为“试用待处理”，持久 state 可由核对任务改为 `expiredUnresolved`，但不得改价格、付款或管理状态。
- 用户确认继续使用时，可将试用标记为 converted，并选择是否进入现有续费流程；只有续费流程才能生成付款和周期。
- 用户确认已取消时，标记为 cancelled，并可同时完成对应取消计划；当前访问结束日仍以订阅 expiry 或取消计划 effectiveEndDay 为准。
- 删除试用计划必须说明只删除计划信息，不删除订阅、周期或付款。

## 4. 取消计划

### 4.1 数据

`CancellationPlanRecord`：

| 字段 | 约束 |
| --- | --- |
| id / subscriptionID | 稳定 UUID 和父订阅 UUID |
| trialPlanID | 可空；取消针对试用时关联同属该订阅的试用计划 |
| trigger | currentPeriodEnd / trialEnd / custom |
| state | planned / submitted / confirmed / revoked / missed / closedByBillingKindChange |
| deadlineDay | 可空；最晚执行取消操作的日期 |
| effectiveEndDay | 可空；服务实际结束访问的日期 |
| submittedAt / confirmedAt | 对应状态下的审计时间戳 |
| confirmationReference | 可选的短文本，不保存密码或完整邮件 |
| note | 可选本地备注 |
| revision / createdAt / updatedAt | 并发与审计字段 |

同一订阅最多有一个处于 planned、submitted 或 confirmed 的未结束计划。历史 revoked、missed 和 closed 记录保留。

### 4.2 状态机

```text
planned ──→ submitted ──→ confirmed
   │              │             │
   ├──────────────┴────────────→ revoked
   ├──────────────→ confirmed
   └── deadline 过去且未提交 ─→ missed
```

- `planned` 只表示用户计划操作。
- `submitted` 表示用户确认已向服务商提交，但结果尚未确认。
- `confirmed` 表示用户确认取消生效；必须填写或确认 effectiveEndDay。
- `revoked` 表示决定继续或服务商取消了原请求。
- `missed` 只表示计划截止时间已过，不能推断服务一定续费或已扣款。
- 任意转移都必须由用户操作或明确的日期核对规则触发，并写入变更记录。
- 新建计划可以从 planned、submitted 或 confirmed 开始，用于如实补录当前事实；直接 planned → confirmed 适用于提交后即时生效的服务，仍需一次明确确认。
- trigger=trialEnd 时必须关联 active 或 expiredUnresolved 的 trial plan；effectiveEndDay 默认建议试用结束日但仍由用户确认。其他 trigger 不得残留 trialPlanID。

### 4.3 与订阅当前字段的关系

- 创建计划不会自动修改 expiry、managementState 或当前价格。
- confirmed 的 effectiveEndDay 与当前 expiry 不同，确认页允许“仅保存取消事实”或“同时把当前到期日更新为结束日”；后一种是同一事务中的显式字段更新。
- 进入 confirmed 时同一事务把 renewalIntent 设为 cancelAtPeriodEnd；进入 revoked 时要求用户明确选择 continueUsing 或 undecided。
- effectiveEndDay 次日只改变派生展示，可提示用户停用；不能自动写 inactive。
- 撤回计划时可把续费意图改为 continueUsing 或 undecided，但必须明确选择。
- 删除订阅时取消计划和试用计划随父记录级联删除，并计入删除确认数量。

## 5. 页面与交互

### 5.1 订阅表单

recurring 表单增加“生命周期”分组：

- 续费意图；
- 可选试用开关及试用日期；
- 可选取消计划入口。

复杂的取消状态转移不塞进普通编辑表单，使用独立 Sheet。所有表单使用草稿；取消不产生写入，保存期间阻止重复提交。

### 5.2 详情

详情顶部状态区可以同时显示：

- 管理状态与到期状态；
- “试用中 / 试用待处理”；
- “准备取消 / 已提交取消 / 已确认至某日结束”；
- “计划继续 / 尚未决定”。

标签不可互相覆盖。例如“使用中 · 7 天后到期 · 已确认到期取消”是合法组合。详情增加“生命周期记录”局部视图，展示试用和取消状态变化，不混入付款或周期表。

### 5.3 表格、首页、时间轴和菜单栏

- 表格筛选增加续费意图、试用中、准备取消和取消待处理；可保存为后续智能视图，但首版不新增松散字符串筛选。
- 首页增加“需要决定”卡片，包含即将结束试用、取消截止日临近和到期前仍 undecided 的项目。
- 时间轴用不同符号显示试用结束与取消截止事件，但订阅到期仍是唯一主锚点；不把三个日期伪装成同一事件。
- 菜单栏速览可增加“待处理”数量和前 3 项，点击进入主窗口；状态项本身仍只显示固定 7 天到期数量。

## 6. 提醒规则

生命周期提醒与现有到期提醒使用同一 `NotificationService`，但拥有独立稳定标识：

- 试用结束：默认提前 3、1 天及当天；
- 取消截止：默认提前 7、3、1 天及当天；
- 续费待决定：在到期提醒中附加“尚未决定”，不额外制造重复通知；
- confirmed 取消只保留访问结束提醒，不再发送“请取消”提醒。

用户可按单个计划关闭提醒。首版沿用全局提醒时间，不增加任意时刻调度。停用订阅时取消其生命周期提醒；恢复时重新验证计划状态后调度。

通知操作只能打开详情、稍后提醒或进入确认流程。不能从通知直接标记已付款、已续费或已取消。

## 7. 费用与统计口径

- active 且尚未到期的 recurring 即使计划取消，在 effectiveEndDay 或 expiry 到来前仍按现有规则参与当前费用预估。
- 试用价格不从当前价格自动推断。若试用实际支付 0，必须由用户登记金额为 0 的付款；否则显示“尚无付款记录”。
- `postTrialBehavior=autoRenews` 仅用于提醒风险，不自动把未来金额记入实际支出。
- 未来费用预测若后续实现，可排除 confirmed 取消且预测日在 effectiveEndDay 之后的周期；planned 或 submitted 仍以“可能发生”单独标记，不能当作确定节省。
- 首页按续费意图展示数量，不把不同币种的潜在节省合计。

## 8. 服务与事务

```swift
struct LifecyclePlanChangeRequest: Sendable {
    let subscriptionID: UUID
    let expectedSubscriptionRevision: Int64
    let expectedPlanRevision: Int64?
    let change: LifecyclePlanChange
}

protocol SubscriptionLifecycleService: Sendable {
    func snapshot(subscriptionID: UUID) async throws -> LifecycleSnapshot
    func prepare(_ request: LifecyclePlanChangeRequest) async throws -> LifecycleChangePreview
    func commit(_ preview: ConfirmedLifecycleChange) async throws -> MutationResult
    func itemsRequiringDecision(on day: LocalDate) async throws -> [LifecycleDecisionItem]
}
```

- 更新订阅意图并创建、修改或关闭计划属于一个事务。
- confirmed 取消同时更新 expiry 时，两者必须原子提交。
- 服务提交成功后统一触发页面、菜单栏、提醒、AI 月度事实和 iCloud mutation 刷新。
- 所有状态变化生成变更事件；日期核对产生的 `missed` / `expiredUnresolved` 也标记为 systemDateReconciliation 来源。

## 9. iCloud、导入导出与 AI

- 试用和取消计划作为独立记录同步，使用自身 revision 和 tombstone；不能嵌进 Subscription 大字段做最后写入覆盖。
- `.periodicdata` 包含计划、状态和关系；CSV 不包含生命周期计划。启用本扩展后的原生 CSV 使用 schemaVersion=2 并增加 renewalIntent 列，旧 CSV 缺失时新建默认 undecided、更新保留原值。
- 整体恢复后重新核对计划状态和通知，不能补发已经过去的所有提醒。
- AI 可查询计划并生成变更提案，但提交、确认取消、撤回或改变到期日仍走原生预览。
- AI 不得把用户一句“我不用了”直接执行为停用、删除或 confirmed 取消。
- AI 月度分析可使用生命周期事件的结构化摘要，默认不发送计划备注或 confirmationReference。

## 10. 错误、冲突与迁移

- 旧订阅迁移后 renewalIntent=undecided，不自动创建试用或取消计划。
- 多窗口同时编辑计划时，revision 不匹配保留草稿并展示本地/新值差异。
- iCloud 同字段冲突需要人工处理；不同计划记录可按关系与状态机验证后合并。
- 日期越界、非法状态转移和重复 active 计划在写入前拒绝。
- 通知失败不回滚已保存计划，但显示可重试状态。
- 服务商实际行为与计划不一致时由用户修正；应用不联网猜测取消结果。

## 11. 测试与验收

### 11.1 自动化测试

- 管理状态、到期状态、续费意图、试用和取消状态全部正交组合。
- 试用及取消日期覆盖今天、月末、闰年、跨年和时区变化。
- 取消状态机合法与非法转移，deadline 过去后的 missed 核对幂等。
- confirmed 取消与 expiry 联合更新的事务回滚和 revision 冲突。
- 续费时撤回取消计划的确认、原子提交和重复点击。
- 生命周期通知去重、停用取消、恢复重排和已过去时刻跳过。
- iCloud 离线修改、tombstone、导入往返和旧数据迁移。
- AI 提案无法绕过确认或把意图误写成管理状态。

### 11.2 验收标准

- **LIFECYCLE-01**：旧数据升级后业务状态不变，续费意图为 undecided。
- **LIFECYCLE-02**：计划取消不会提前停用、过期、删除或移出当前有效口径。
- **LIFECYCLE-03**：试用结束不会自动产生付款、周期、续费或价格变化。
- **LIFECYCLE-04**：planned、submitted、confirmed、revoked 和 missed 具有明确且受校验的状态转移。
- **LIFECYCLE-05**：confirmed 取消更新到期日必须由用户明确选择并原子提交。
- **LIFECYCLE-06**：续费与未结束取消计划冲突时必须先处理计划，不能静默覆盖。
- **LIFECYCLE-07**：生命周期提醒与到期提醒分别去重，关闭或停用后不残留。
- **LIFECYCLE-08**：表格、首页、时间轴、详情和菜单栏使用同一生命周期快照。
- **LIFECYCLE-09**：金额、实际付款和潜在节省保持不同事实且不跨币种合计。
- **LIFECYCLE-10**：同步、导入、AI 和多窗口均遵守 revision、事务与确认边界。
- **LIFECYCLE-11**：日期任务只更新允许的派生/计划状态，不修改管理状态和财务事实。
- **LIFECYCLE-12**：键盘和 VoiceOver 可识别每种状态、截止日和确认动作。

## 12. 分阶段落地

1. 定义续费意图、试用/取消计划值类型、状态机和模型迁移。
2. 实现 Lifecycle Service、事务、变更事件和领域测试。
3. 接入订阅表单、详情状态及独立计划 Sheet。
4. 接入筛选、首页“需要决定”、时间轴和菜单栏快照。
5. 接入通知、跨日核对、iCloud 和数据包。
6. 扩展 AI 工具与月度分析事实，完成多窗口和可访问性验收。
